# Email notifications: setup and first test

The backend sends plain-text notifications through Hostinger SMTP or another
SMTP provider. The first event is an explicit test request:
`POST /api/v1/notifications/test-email`. It sends
only to the signed-in user's email from the database. There is no recipient or
message input. Both email sending and this diagnostic event are disabled by default.

`EmailService` composes messages and sends them through SMTP; `NotificationService.send_test` supplies the event's
subject and body. Sending runs in FastAPI's worker thread and the request waits for
the provider result. No new package or database migration is required. Invitations,
polls, and other application actions do not send notifications yet.

## Hostinger Email with your custom domain

Use SMTP to send notifications. IMAP reads incoming mail and is not needed for
this feature. The existing SMTP sender supports Hostinger without code changes.

1. Create or choose a mailbox in Hostinger, such as `notifications@yourdomain.com`.
2. Check that your domain's email DNS setup is complete in Hostinger's email
   dashboard, including MX, SPF, and DKIM. Use Hostinger's current DNS
   instructions for your domain.
3. Confirm the outgoing server settings shown for your mailbox. Hostinger Email
   documents `smtp.hostinger.com`, port `465`, with SSL/TLS. See
   [Hostinger's setup guide](https://www.hostinger.com/support/4305847-set-up-hostinger-email-on-your-applications-and-devices/).

Edit the existing root `.env`, preserving your database and JWT values:

```dotenv
EMAIL_ENABLED=true
EMAIL_TEST_ENABLED=true
EMAIL_FROM_ADDRESS=notifications@yourdomain.com
EMAIL_FROM_NAME=Group Travel Planner
EMAIL_TIMEOUT_SECONDS=10
SMTP_HOST=smtp.hostinger.com
SMTP_PORT=465
SMTP_ENCRYPTION=ssl
SMTP_USERNAME=notifications@yourdomain.com
SMTP_PASSWORD='replace-with-your-mailbox-password'
```

Replace both email addresses with your actual mailbox. Use the mailbox password
for SMTP authentication; see [Hostinger's SMTP example](https://www.hostinger.com/tutorials/how-to-send-emails-using-phpmailer/).
Keep the password in your local backend environment and out of Git.

Restart the backend (`pnpm run dev:backend`), then follow **Trigger the test event**
below. If your mailbox settings specify STARTTLS, set `SMTP_PORT=587` and
`SMTP_ENCRYPTION=starttls` together. Confirm the actual server in your dashboard
if your account uses a different email product.

For Docker, put the values in `docker/.env` and recreate the backend container to
apply them. Both Compose definitions already forward these settings. The development
backend applies migrations and starts FastAPI automatically; see the README for
the complete Docker setup.

## Other SMTP providers

Set `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, and
`SMTP_PASSWORD` using your provider's settings, along with `EMAIL_FROM_ADDRESS`.
Use `SMTP_ENCRYPTION=starttls` for STARTTLS (usually port 587), or `ssl` for TLS
from connection start (usually port 465). TLS certificates are verified; STARTTLS
failure never falls back to plaintext. Credentials must be provided together.
For Hostinger, use the SMTP configuration above.

## Trigger the test event

Start the migrated database, Redis, and backend as described in the README. Sign in with a
registered account whose email is a mailbox you control. From PowerShell you can
log in and send the event using the same session:

```powershell
$api = 'http://localhost:8000/api/v1'
$headers = @{ 'X-CSRF-Protection' = '1' }
$credential = Get-Credential -Message 'Enter your app email and app password'
$loginBody = @{
    email = $credential.UserName
    password = $credential.GetNetworkCredential().Password
} | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$api/auth/login" `
    -Headers $headers -ContentType 'application/json' `
    -Body $loginBody -SessionVariable travelSession
Invoke-RestMethod -Method Post -Uri "$api/notifications/test-email" `
    -Headers $headers -WebSession $travelSession
```

The response is HTTP 200 with:

```json
{
  "status": "accepted",
  "message_id": "<unique-message-id@yourdomain.com>"
}
```

Check your inbox (and spam folder) for **Group Travel Planner: test notification**.
`accepted` means the provider accepted the message, not that it reached the
inbox. The returned `message_id` is generated by this app and included in the
message; it is not a delivery receipt.

The existing CSRF middleware also requires a trusted `Origin` for browser requests.
The test endpoint has no body and ignores any supplied recipient; it always uses
the authenticated account. Existing registration does not verify mailbox ownership.
Keep this diagnostic enabled only in a controlled test environment, then set
`EMAIL_TEST_ENABLED=false` and restart/recreate the backend. It has no rate limiter.

## Local test without credentials or DNS

[Mailpit](https://mailpit.axllent.org/docs/install/docker/) captures messages locally
instead of sending them to real inboxes. With Docker running:

```sh
docker run --rm --name travel-mailpit -p 127.0.0.1:1025:1025 -p 127.0.0.1:8025:8025 axllent/mailpit
```

For a backend running on your host, use these root `.env` values:

```dotenv
APP_ENV=development
EMAIL_ENABLED=true
EMAIL_TEST_ENABLED=true
EMAIL_FROM_ADDRESS=notifications@example.com
EMAIL_FROM_NAME=Group Travel Planner
SMTP_HOST=127.0.0.1
SMTP_PORT=1025
SMTP_ENCRYPTION=none
SMTP_USERNAME=
SMTP_PASSWORD=
EMAIL_TIMEOUT_SECONDS=10
```

Restart FastAPI, trigger the event above, and open <http://localhost:8025> to view
the message. These loopback settings are for a host-run backend; a container's
`127.0.0.1` points to that container. Unencrypted SMTP is allowed only in
`development`/`test`, without credentials. Stop Mailpit with Ctrl+C when finished.

## Troubleshooting and limits

| Result                      | Meaning / next step                                                          |
| --------------------------- | ---------------------------------------------------------------------------- |
| Startup configuration error | Supply a valid sender and the required SMTP settings.                        |
| HTTP 401                    | Sign in first and preserve the app session cookie.                           |
| HTTP 403                    | Include `X-CSRF-Protection: 1`; browser origins must be in `CORS_ORIGINS`.   |
| HTTP 404                    | Enable `EMAIL_TEST_ENABLED` and restart the backend.                         |
| HTTP 503                    | Enable `EMAIL_ENABLED` and configure SMTP.                                   |
| HTTP 502 (SMTP)             | Check host/port, credentials, TLS, sender verification, and provider limits. |
| Accepted, no inbox message  | Check spam, the provider dashboard, and DNS authentication.                  |

Provider failures are returned as a generic error. Server logs contain only the
failure class, without tokens, credentials, recipient addresses, or provider bodies.

This first version does not queue or retry messages and does not track delivery.
A timeout or disconnect can happen after a provider accepts a message, so a failed
request does not always mean nothing was sent. A manual retry may send a duplicate.
Before connecting important business events, add a durable outbox/worker, retries,
deduplication, verified recipients, notification preferences, and delivery tracking
as appropriate. A plain-text test event needs none of those database changes.
